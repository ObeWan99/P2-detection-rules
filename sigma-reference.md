# Справочник к практике 2. Правила Sigma и оценка их качества

[English version](sigma-reference.en.md)

## 1. Формат Sigma

**Sigma** — открытый формат описания правил обнаружения, не зависящий от конкретной SIEM. Правило записывается один раз
в текстовом файле формата YAML и затем автоматически переводится на язык запросов нужной системы (Elastic, Splunk, KUMA и др.).

Правила YAML: каждая строка — пара «ключ: значение»; вложенность задаётся отступами из пробелов (символ табуляции недопустим).

## 2. Структура правила

```yaml
title: Сканер уязвимостей в User-Agent
logsource:
  category: webserver
detection:
  selection:
    event.dataset: web
    user_agent.original|contains:
      - sqlmap
      - nikto
  condition: selection
level: medium
```

| Поле | Назначение |
|---|---|
| `title` | Название правила; отображается дежурному при срабатывании |
| `logsource` | Категория журналов, к которым применяется правило |
| `detection` | Условия обнаружения (раздел 3) |
| `level` | Уровень важности: `low`, `medium`, `high`, `critical` |

Полные правила содержат также идентификатор (`id`), автора, описание, привязку к MITRE ATT&CK (`tags`) и перечень
возможных ложных срабатываний (`falsepositives`). В практике используется минимальный набор полей.

## 3. Раздел `detection`

| Запись | Значение |
|---|---|
| Несколько полей в одном условии | Логическое **И**: должны выполняться все |
| Список значений (строки, начинающиеся с `-`) | Логическое **ИЛИ**: достаточно одного |
| `поле: значение` | Поле равно значению |
| `поле\|contains: текст` | Поле содержит текст |
| `поле\|cidr: '10.0.0.0/8'` | IP-адрес принадлежит диапазону (здесь — все адреса `10.x.x.x`) |
| `поле\|exists: true` | Поле присутствует в событии |
| `selection`, `filter` | Именованные условия: что ищем и что исключаем |
| `condition: selection and not filter` | Срабатывание при выполнении `selection`, за исключением случаев `filter` |

Используются названия полей схемы ECS из практики 1: `event.action`, `source.ip`, `url.original`, `user_agent.original`,
`process.name`, `process.command_line` и др.

### Где найти значения для правила

Discover → представление со всеми нормализованными журналами (`norm-*`) → период — неделя данных, 10–16 марта 2025 (как в П1). Сначала **сузить события запросом**, потом
щёлкнуть поле слева и посмотреть топ значений:

| Заготовка | Запрос в строке поиска | Поле |
|---|---|---|
| `01` | `event.dataset : "web"` | `user_agent.original` — значения, не похожие на браузер |
| `02` | `event.dataset : "system"` | `event.action` — подключение по SSH |
| `03` | `process.name : *` | `process.name` |
| `04` | `process.command_line : *` | `event.action`, затем `process.command_line` |
| `05` | `event.dataset : "auth"` | `event.action` — успешный вход |

Без запроса топ считается сразу по трём журналам (событий около 50 тысяч, разных `event.action` — 21), Kibana показывает
только 10 самых частых значений, а редкие собирает в строку **Other**. Запрос оставляет только нужный журнал или только события,
где поле заполнено, — и нужное значение попадает в топ.

## 4. Оценка качества правила

### 4.1. Матрица ошибок

Каждое событие журнала относится либо к атаке, либо к нормальной работе; правило на каждое событие либо срабатывает,
либо нет. Отсюда четыре возможных исхода:

| | Правило сработало | Правило не сработало |
|---|---|---|
| **Событие — атака** | **TP** (true positive) — верное срабатывание | **FN** (false negative) — пропуск атаки |
| **Событие — норма** | **FP** (false positive) — ложное срабатывание | **TN** (true negative) — верное отсутствие срабатывания |

Те же четыре исхода описывают любой диагностический тест. Например, тест на инфекцию: болен и тест положительный — TP;
здоров, но тест положительный — FP; болен, но тест отрицательный — FN; здоров и тест отрицательный — TN.
Ложное срабатывание (FP) также называют ошибкой первого рода, пропуск (FN) — ошибкой второго рода.

### 4.2. Точность (precision)

**Точность = TP / (TP + FP)**

Доля верных срабатываний среди всех срабатываний правила. Показывает, насколько можно доверять сигналу.

*Пример.* Правило «успешный вход с внешнего адреса» сработало 784 раза; 397 из них — события атаки, 387 — входы удалённых
сотрудников. Точность = 397 / 784 = 0,51, то есть 51 %: каждый второй сигнал ложный.

### 4.3. Полнота (recall)

**Полнота = TP / (TP + FN)**

Доля обнаруженных событий атаки среди всех событий атаки. Показывает, какая часть атаки замечена.

*Пример.* На этапе «подбор пароля и вход» атака состоит из 1 582 событий; правила обнаружили 397 (успешные входы).
Полнота = 397 / 1 582 = 0,25, то есть 25 %: неудачные попытки входа правилами не обнаружены.

### 4.4. Почему не используется доля верных ответов

Доля верных ответов (accuracy) = (TP + TN) / (TP + TN + FP + FN). Для правил обнаружения эта мера непригодна:
нормальных событий значительно больше, чем событий атаки, и большое значение TN делает высоким результат любого правила.

*Пример.* В учебных данных 50 000 событий, из них 3 093 — атака. Правило, которое не срабатывает никогда, имеет
TN = 46 907 и долю верных ответов 46 907 / 50 000 = 93,8 % — при полноте 0 %.

Поэтому качество правил обнаружения оценивают по точности и полноте; TN в них не входит.

### 4.5. Компромисс точности и полноты

Расширение правила (новые значения в списке, меньше исключений) повышает полноту, но, как правило, снижает точность.
Сужение правила (исключения `filter`, более строгие условия) повышает точность, но может снизить полноту.
Каждое исключение создаёт область, в которой правило не сработает и на настоящую атаку.

## 5. Работа на стенде

В папке `P2-detection-rules`, стенд П1 запущен:

```bash
docker compose run --rm p2 rules     # перевести правила из папки rules/ и создать их в Kibana
docker compose run --rm p2 score     # рассчитать точность каждого правила и полноту по этапам атаки
```

Для расчёта используется разметка учебных данных (`tools/ground_truth.csv`) — перечень всех событий атаки.
В реальной эксплуатации разметки нет: точность оценивают по результатам разбора сигналов дежурными,
полноту — в ходе учений, когда атака проводится намеренно.
